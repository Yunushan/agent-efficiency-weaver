# Architecture

The Python core stays dependency-free at runtime and reads public data from `catalogs/`, `profiles/`, and `.agents/skills/`. Installed distributions copy that allowlisted data into the package; `src/agentweaver/resources.py` resolves it with `importlib.resources`. An explicit `--root` overrides bundled resources only for intentional source or custom work, with no checkout or CWD fallback. Editable development uses `--root .` plus `PYTHONPATH=src`.

## Data and evidence model

`catalogs/integrations.json` is the source of truth for 31 products: 25 agents, 4 providers, and 2 hybrids, with stable product and surface IDs. Runtime parsing validates the schema and identities without fixing the product count in Python. Pure providers require metadata on every surface; hybrids require both provider and application/MCP-host surfaces. Each surface records its MCP dialect, config scope, documented path hint, instruction mode and paths, skills path, OS workflow states, and evidence for `mcp`, `instructions`, `skills`, `provider`, and `os`. Evidence fields `sources`, `checked_on`, `version_constraint`, `fixture_tests`, and `runtime_checks` are independent. A catalog entry, fixture test, or portable Python implementation is not installed-version or native-device evidence.

`catalogs/requested-coverage.json` maps the user's 23 requested groups to 34 distinct registry surfaces and records explicit aliases. `src/agentweaver/coverage.py` checks every reference and rejects alias collisions and canonical-ID shadowing. Its report distinguishes mapping from capability states, missing documentation, fixture references, and pending runtime checks. The multi-product VS Code group is inspectable but cannot resolve to one exporter.

`catalogs/model-providers.json` records documented provider/protocol routes, discovery formats and dated reasoning examples separately from product identity. `src/agentweaver/models.py` normalizes caller-supplied model snapshots, records provenance without local filesystem paths, accepts explicit model IDs without implying access, and validates reasoning against specific model/protocol evidence. Dynamic catalogs remain open; the known examples are not an exhaustive model list. Snapshot visibility and documented reasoning controls do not establish inference, account access, or runtime consumption.

OpenRouter conditional pricing is preserved with its conditions; no active tier or bill is inferred. Observed unresolved `-1` values become unknown prices with raw-value observations, never zero. Architecture and supported reasoning metadata survive normalization. Known non-text models remain task-specific manual handoffs and cannot silently become native language-agent overrides; absent modality information remains unknown. Catalog capture filters are separate from the offline importer, including OpenRouter's explicit all-modalities query.

A provider-reported `context_length: 0` is preserved in snapshot inventory, while the derived usable `context_size` remains `None` until a positive model limit is established. Explicit zero or other invalid context overrides fail validation. Kimi native model configuration requires a positive supplied or documented snapshot limit; an unknown limit leaves a manual template.

`catalogs/model-hosts.json` records selection mechanisms, fields, session commands, UI guidance, and model-dependent reasoning controls for all 43 registered surfaces. `load_model_hosts` requires exactly one row per product/surface. These operator-facing documentation states are separate from provider/backend discovery and native model exporters; the catalog cannot activate an exporter. Unknown availability and pending runtime evidence remain explicit. Null allowed values require discovery in the chosen host/model rather than borrowing a vocabulary from another surface.

`catalogs/operating-systems.json` records seven families: Windows, macOS, Linux, BSD, Solaris, Android, and iOS. Windows, macOS, and Linux are primary CI targets. BSD and Solaris require Python 3.11+ and real-host evidence, Android is conditional Termux/compatible Python plus remote handoff, and iOS is remote/artifact handoff only. Host detection preserves WSL, BSD variant, and illumos qualifiers.

## Rendering pipeline

`src/agentweaver/integrations.py` parses registries strictly and exposes frozen specification records. `src/agentweaver/adapters.py` maps only implemented product surfaces to documented dialect fragments, dispatching on the registry dialect ID; project-scope dialects are staged under `<agent>/<native path>`, user-scope fragments under `<agent>/fragments/`, and request-scope bodies under `<agent>/requests/<surface>.json`. Request artifacts are not native configuration files or API calls. App-managed manual surfaces do not receive a guessed MCP configuration path. The exporter does not infer a schema from a similar product name.

Qoder IDE has a documented app-scope JSON import fragment under `qoder/fragments/` with no inferred persistent MCP filename. Its root project instructions and native Skills path are separate contracts. Stdio evidence includes an additional Qoder IDE dialect route and the OpenHands CLI manual user-file route, giving 27 matching surfaces across 23 products; sources and schemas are tracked for each route rather than inferred from the CLI. JetBrains Air remains the unestablished stdio file-export route.

`src/agentweaver/config.py` validates remote HTTPS and structured stdio catalog entries, keeps all selections default-off, and applies profile allowlists before rendering. A stdio selection preserves one executable and an argument array. Product-specific stdio evidence and serialization live in `adapters.py` independently of the remote URL dialect: a similar JSON root does not establish stdio compatibility. Request-only Perplexity and LM Studio ephemeral MCP fragments reject local stdio. No renderer expands variables, invokes a shell, installs packages, starts a server, or tests an executable.

The `perplexity` API MCP and `perplexity-computer` Computer MCP catalog entries have distinct endpoints and remain default-off. Computer requires host-managed account OAuth, consumes account credits and may expose connected-service write actions. Its `models_list` result is account-scoped; it is not a provider API catalog. Weaver exports no authentication material and performs no OAuth, connection or task execution.

GitHub's hosted MCP entries provide separate default and all-toolset URLs, each with an explicit read-only alternative. They remain absent from shipped profile allowlists and require explicit selection. GitHub's read-only URL is a server-side tool filter for that connection; it does not restrict other servers, grant account permissions or turn profile advice into host enforcement. The non-read-only variants can expose write tools. No OAuth, token, connection or runtime verification is performed by staging.

The `openai-docs` catalog entry is OpenAI's documentation-only remote MCP server; it is default-off and absent from shipped allowlists. It is distinct from hosting Codex as an MCP server. OpenAI's current migration guidance says `codex mcp-server` and the standalone server binary were removed; the experimental app server uses its own JSON-RPC protocol and is not an MCP drop-in. The catalog does not stage a legacy Codex MCP launcher or app-server process.

The separate `computer-models` offline command reads a caller-supplied raw `models_list` response, retains documented model/mode fields and a content hash, and validates an optional mode or model with model-specific effort. Missing effort metadata remains unknown, mode and model are mutually exclusive, and a snapshot is not proof of current entitlement or successful inference. Unknown response fields are scanned for secret-like material but not retained; no account endpoint or MCP tool is invoked.

The `kimi-models` offline command reads a caller-supplied successful Kimi web model-list envelope and treats `data.items[].model` as a configured alias. It preserves source-specific thinking efforts and optional replacement metadata without converting aliases into upstream IDs. Unknown fields, request IDs and migration text are not retained; credential-bearing content is rejected. Neither inspector connects to a provider or establishes current account access.

`src/agentweaver/skills.py` validates the six canonical skills and projects only documented instruction or skill mechanisms, with explicit manual handoffs where native discovery is unavailable. Cline, Cursor and Qoder IDE now have documented native Skill directories. Perplexity app and LM Studio Bionic stage standard files under `<product>/imports/skills/<name>/SKILL.md` for manual vendor import, independently of native discovery. Other manual read-file routes and Abacus stage `<agent>/read/<name>.md` files that the instruction file links to; Abacus receives only the root `AGENTS.md` and no native skill directory. `catalogs/custom-agents.json` and `src/agentweaver/agents.py` inventory custom-agent definition routes separately from project instructions and portable Skills. A native agent-definition artifact follows a documented format; a manual route receives a handoff, and unknown or unsupported routes fail closed. Model, reasoning, and permission behavior remain specific to the definition route.

Devin Desktop Local has an experimental native profile route with a true read/search tool restriction and an operator-enabled Preview prerequisite. Its omitted model resolves through the configured subagent default/router/admin policy rather than parent inheritance. Perplexity Agent API has a manual versioned Profile workflow and request-reference example; it does not serialize a guessed creation schema or treat Profiles as an authorization boundary. Reviewed Preset, Skill, built-in delegation and request-control evidence leaves five requested custom-definition routes unknown where no distinct registration contract is established.

Air in IDEs is registered independently as `jetbrains-air/ide`. Its custom-agent route is a manual UI preset using injected instructions; it does not serialize a native subagent file or ACP registration. Bundles stage selected portable Skills as ordinary `read/<name>.md` context, with no claimed import loader. Host Skills selection, model and effort controls remain agent-dependent; MCP file export, arbitrary OpenRouter configuration and a complete IDE OS matrix are unestablished. Air desktop configuration and OS documentation are not transferred to this plugin.

OpenHands custom-agent discovery is bound by source to CLI 1.16.0 and SDK 1.28.1, rather than inferred from generic SDK documentation. The exporter stages `.agents/agents/<name>.md` with `model: inherit` by default and `tools: []`. The separate `--llm-profile` option records an existing named local LLM profile reference in `model`, preserving its exact spelling without reading the profile store or credentials, checking existence, or creating a profile. It conflicts with raw model, provider, catalog and effort overrides. The SDK resolves the reference during later manual use; configured provider/model, reasoning, availability and inference remain unknown. Top-level file discovery, registration precedence and remaining base finish/think behavior are documented separately from OS sandboxing. Its instructions and Skills loaders check the working directory and then Git root, with canonical Skills in immediate child directories; no general ancestor or category recursion is promised.

`src/agentweaver/providers.py` preserves legacy OpenRouter handoffs and requires explicit model selection. Each implemented surface produces `<agent>/provider/provider-setup.md`; Codex also produces `codex/provider/config.toml`, a credential-free native TOML fragment. Other model setup uses `<product>/model/model-setup.md` and `model-selection.json`, with native configuration fragments only for implemented routes and manual handoffs otherwise. Unknown reasoning settings are refused rather than silently substituted.

Codex custom-provider fragments target a deliberate user-level merge and declare Responses wire behavior; project-local provider keys are ignored. ChatGPT desktop and Work local have a manual Responses-compatible handoff, while web and Work Cloud retain a separate boundary. Host metadata records the actual provider-selection mechanism, including reviewed gaps where a tool credential or LM Link remote model is not a custom inference-provider setting.

OpenHands model/provider setup uses the CLI command palette, `Ctrl+P` > Settings, and persisted `Agent.llm` configuration. `--override-with-envs` explicitly enables temporary, nonpersisted process overrides. The pinned SDK supplies model-dependent `llm.reasoning_effort` and `llm.extended_thinking_budget`; effort is omitted on its Responses subscription route and Chat thinking budgets are capped below `max_output_tokens`. Those manual host controls do not add custom-agent reasoning fields or a native settings exporter. JetBrains Air desktop alone retains an unknown shared reasoning override.

`src/agentweaver/artifacts.py` validates every relative path and content before writing. It refuses links, junctions, traversal, absolute paths, conflicting destinations, and unmanaged overwrites. Manifest entries record relative paths, hashes, and kinds; hashes support change detection, not signatures or audit guarantees. The writer is not a bundle-wide atomic transaction and does not claim cross-process race resistance.

## Diagnostics and boundaries

`src/agentweaver/platforms.py` keeps core-runtime eligibility, adapter availability, vendor-native availability, manual routes, and remote routes separate. Structured runtime checks must identify the exact product/surface and product version, match the host OS variant and architecture, and record configuration consumption, installation state, date and artifact hash. Missing identity fields, a version-only observation, another product's result or another host's record cannot establish strict readiness. The API accepts operator-supplied records without authenticating their provenance; registry file references are not automatically imported. `doctor` reports pending evidence and never installs or launches tools. Rendering a target-OS handoff does not imply that files execute on that target.

Conflicting `target_os`, `os`, or `host_os` aliases in one record are rejected unless they normalize consistently. Matching pass and fail observations remain unknown regardless of input ordering; the diagnostic does not pick a winner by timestamp. Reviewed OS documentation remains separate: the requested-surface table records exact states and constraints, while all 170 requested runtime capability records remain pending.

Generated MCP selections are default-off and staging-only. The `enterprise-secure` profile generates zero MCP selections for staged output; ambient and global vendor configuration is not inspected. Profile retrieval rules are advisory and not tool enforcement. Nothing in the ordinary coverage, model inventory/setup, Computer or Kimi snapshot inspection, agent definition, render, bundle, provider, doctor, report, or compare path performs network access, credential discovery, agent execution, production writes, or paid calls. Provider URLs and environment references are public metadata; a missing documented environment name stays null. HTTP is restricted to explicit LM Studio loopback metadata, without enabling a local service.

Benchmark code remains independent of integration rendering. Missing token or cost data stays unknown, synthetic fixtures stay separate from measured evidence, and no numerical efficiency claim is derived from catalog metadata.

`scripts/check-readiness.py` runs the six required offline release gates with pinned development tools and hashes the relevant public source inputs before and after the run. Its scoped score describes only that local gate run; native vendor checks and other host combinations require separate evidence. `scripts/verify-platform.py` records source-version provenance and a smaller local validation/test run, with native verification explicitly pending. Neither tool upgrades registry runtime evidence automatically.

The readiness guide records separate immutable CI checkpoints for the earlier 20-product release and the initial 31-product expansion. Each later candidate requires its own gates and primary-host evidence; vendor-runtime records remain separate.
